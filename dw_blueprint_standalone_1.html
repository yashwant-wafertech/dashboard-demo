04 · Data model

A star schema, not a spreadsheet

Every metric on the dashboard traces back to two fact tables and four shared dimensions. This is what makes "add a segment" or "filter by circle" instant, instead of a re-export.

05 · Metric logic

The same numbers, computed the way a warehouse computes them

In the demo these are JavaScript. In production they're SQL window functions over the fact tables above — auditable, consistent across every dashboard that reads them, and correct even when a date is backfilled or corrected.

GDD / MTD / YTD / YOY deposit growth Period-over-period deltas via window functions 
-- Growth Day-on-Day, Month/Year-to-Date, Year-on-Year, per branch
SELECT
  d.calendar_date,
  b.branch_code,
  SUM(f.closing_balance) AS total_deposits,
  SUM(f.closing_balance) - LAG(SUM(f.closing_balance), 1)
    OVER (PARTITION BY b.branch_code ORDER BY d.calendar_date) AS gdd,
  SUM(f.closing_balance) - FIRST_VALUE(SUM(f.closing_balance))
    OVER (PARTITION BY b.branch_code, d.month_start_date ORDER BY d.calendar_date) AS mtd,
  SUM(f.closing_balance) - FIRST_VALUE(SUM(f.closing_balance))
    OVER (PARTITION BY b.branch_code, d.fiscal_year_start_date ORDER BY d.calendar_date) AS ytd
FROM fact_account_balance_daily f
JOIN dim_date d ON f.balance_date_key = d.date_key
JOIN dim_branch b ON f.branch_key = b.branch_key
GROUP BY d.calendar_date, d.month_start_date, d.fiscal_year_start_date, b.branch_code
Gross NPA classification & NPA% RBI IRAC norms — 90+ days past due 
-- Flag NPA at the fact grain, then roll up to a ratio per segment
SELECT
  s.segment_name,
  SUM(CASE WHEN f.days_past_due >= 90 THEN f.outstanding_amt ELSE 0 END) AS gross_npa,
  SUM(f.outstanding_amt) AS total_advances,
  ROUND(
    100.0 * SUM(CASE WHEN f.days_past_due >= 90 THEN f.outstanding_amt ELSE 0 END)
    / NULLIF(SUM(f.outstanding_amt), 0), 2
  ) AS npa_pct
FROM fact_advance_outstanding_daily f
JOIN dim_segment s ON f.segment_key = s.segment_key
WHERE f.balance_date_key = 20260830
GROUP BY s.segment_name
CASA % Savings + current, as a share of total deposits 
SELECT
  b.circle_name,
  ROUND(
    100.0 * SUM(CASE WHEN p.product_type IN ('SB','CA') THEN f.closing_balance ELSE 0 END)
    / NULLIF(SUM(f.closing_balance), 0), 2
  ) AS casa_pct
FROM fact_account_balance_daily f
JOIN dim_branch b ON f.branch_key = b.branch_key
JOIN dim_product p ON f.product_key = p.product_key
WHERE f.balance_date_key = 20260830
GROUP BY b.circle_name

06 · Why it matters

What changes between the demo and production

Today's demo (Bank Pulse)
  • Numbers live in a spreadsheet or Google Sheet
  • Deltas are computed once, by hand, in JavaScript
  • No history — only the values you typed in
  • Anyone with the link can see everything
  • Refresh means someone re-pastes numbers
Production warehouse
  • Numbers flow nightly from the core banking system
  • Every metric is one governed SQL definition, used everywhere
  • Full daily history — audit any date, backfill corrections
  • Row-level security — a circle head sees only their circle
  • Refresh is automatic, monitored, and alerts on failure
💡

The pitch, in one line: everything you just saw in Bank Pulse is possible today with a spreadsheet — imagine it running on real balances, refreshed every night, with the audit trail RBI reporting requires. That's the warehouse build.

Reference architecture and SQL are illustrative — table names, grain, and metric definitions would be finalised against your actual core banking schema during discovery.
